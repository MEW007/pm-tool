# AI Coding Agent Instructions – PM Tool

## Project Overview
An **online project management tool** that runs projects through meetings. On launch the user logs in, selects a project and works inside that project environment: team, meetings and minutes, actions, decisions, risks and a dashboard.

- **Owner:** Ward Mertens (Dutch speaker; the tool UI is English)
- **Users:** small team, every editor logs in; access is granted per project
- **Build plan and progress tracking:** [`BUILD_PLAN.md`](BUILD_PLAN.md). Read it before starting any work, and update its checkboxes and progress log after each work session.

**KEY requirement:** this is a real, hosted tool with a persistent database. Do not build mock-ups, local-only storage (`localStorage`) or hard-coded sample data as a substitute for the database.

---

## Stack
- **Frontend:** Vite + React + TypeScript, hosted on **GitHub Pages**, deployed by GitHub Actions
- **Backend:** **Supabase** (Postgres, EU region) with Supabase Auth (magic link, sign-up disabled)
- **Security:** Row Level Security on every table, scoped by `project_id` and project membership
- **Secrets:** only the Supabase URL and the anon key go into the frontend (via env/build vars). Never commit the service role key or database password.

---

## Domain model (summary; full model in BUILD_PLAN.md §4)
- **Project** → has **team members** (name, email, role, company; optionally linked to a login with access level `admin`/`editor`).
- **Meeting series** (subject + code, e.g. `WPM` "Weekly progress meeting") → **meetings** with a follow-up **number**, date, attendees and status `Draft`/`Issued`.
- **Minute items** per meeting, type `Info`, `Action`, `Decision` or `Risk`. Reference format `<series>-<meeting no>-<item no>`, e.g. `WPM-03-02`.
- **Actions** come from action items. Every change is logged in **action_updates** with the `meeting_id` it was made in (null if made outside a meeting).
- **Decisions** are minute items of type `Decision`, optionally linked to an earlier action.
- **Risks** live in a register and can also be raised from a `Risk` minute item (linked both ways). Changes are logged in **risk_updates**.

### Follow-up rule (core behaviour, do not break)
A new meeting in a series shows all open actions for review. Each review is stored as an `action_update` linked to that meeting. It must always be traceable **when and in which meeting** an action was raised, updated, re-planned, decided on or closed. Issued minutes show the action status as recorded in that meeting, not today's status.

## Conventions
- **Dates:** ISO 8601 (YYYY-MM-DD). **Time:** 24-hour (HH:MM).
- **Action status:** `Open`, `In Progress`, `Done`, `Cancelled` (DB: `open`, `in_progress`, `done`, `cancelled`).
- **Priority:** `High`, `Medium`, `Low`.
- **Risk status:** `Open`, `Mitigating`, `Closed`, `Occurred`. Probability and impact 1–5, score = P × I.
- **Attendance:** `Present`, `Excused`, `Absent`, `Distribution only`.
- **Every action needs an owner and a due date.**
- **Indentation:** 2 spaces.
- **DB changes:** only through numbered SQL migrations in `supabase/migrations/`. Never change the schema by hand in the Supabase dashboard without adding the matching migration.
- **Naming:** DB tables and columns in `snake_case`; TypeScript in `camelCase`; React components in `PascalCase`.
